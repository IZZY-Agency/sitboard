# Changelog

## 0.6.0

Which agents are on each issue or looked at it, issues you pin, GitLab issues, a start-up block in the page's colours, and a tab that says when sitboard has stopped.

What is new:

- Issues and agents. Each issue the Issues panel lists can now name the agents on the board that are on it ("on it": an open pull or merge request their session opened closes it) or looked at it ("looked at": their session's own `gh issue` or `glab issue` command named it), or say "no agent seen". An Agent filter shows only the issues with no agent seen, or only those with an agent. Project tiles can add "N with no agent seen", and a card can say "looked at #N". The commands read are `gh issue view`, `comment`, `edit`, `develop`, `close` and `reopen`, and `glab issue view`, `note`, `update`, `close` and `reopen`. "Looked at" comes only from sessions on the board that have not ended and are not coordinators, and only for issues in the list; "on it" can also name an issue outside it (see Limits).
- Pinned issues. A star on each issue pins it: pinned issues lead their repository's list under "Pinned", and the pins are saved in sitboard's state file; when sitboard runs without a writable state (for example with `--no-state`) they last until it stops, and the panel says so. Up to 200 issues can be pinned. A pinned issue that is not among the 30 listed can show under "Pinned" too. On GitHub, sitboard asks for it by number in the lookup it already makes, and the row shows its title once GitHub has answered; a pin GitHub reports closed says "closed since you pinned it" and goes 7 days after sitboard first saw it closed, unless GitHub reports it open again first, and a pin GitHub reports does not exist can be unpinned. Nothing is asked of GitLab for such a pin, so its row shows no title. On either forge the row shows the agents whose open pull or merge request closes the issue.
- Issues on GitLab. The Issues chip, the Issues panel, project tiles and rail rows now count and list the open issues of GitLab projects too, read only and grouped by milestone like GitHub's, each number linked to GitLab. They are asked through your own `glab`, for a host name whose glab login check passed in the last ten minutes (gitlab.com, self-hosted, under a subfolder or on a web port alike): glab sends the lookups where its own configuration for that name points, and sitboard leaves out a project whose answer names another address than the one it asked about. They are asked in the same ten-minute looks as GitHub's, at most 8 projects to a call. A GitLab repository not answered yet, not found or with issues turned off says so. `--no-gitlab` turns it off.
- A page whose sitboard has stopped says so. A short loss of the connection still says "Reconnecting"; after about half a minute without contact, the header's chip reads "Stopped · last update HH:MM", the banner says sitboard has stopped answering and that what is shown may be out of date, the board is dimmed further, and the tab's title ("sitboard · stopped") and icon say it is not live instead of a count of agents that need you. The ages on the cards stay where they were when the connection was lost. While it says Reconnecting or Stopped, the last board stays on the page. The page keeps trying in the background: if sitboard comes back in the same run, the page is live again by itself. A new run has a new private link: the old tab may say "This tab lost its key" in place of the board; open the new link.
- In a terminal, sitboard starts with one block in the page's colours: its name and version, the private link for this run on a line of its own, a line per source (Claude Code, Codex, agterm, git, GitHub through gh, GitLab through glab, tmux) with what it found as it started or when it will look, the state file notes and "press Ctrl-C to stop". It is printed once and never redrawn. Piped to a file or another program, or with a non-empty `NO_COLOR` or `TERM=dumb`, the start lines are plain text. A terminal that sets `COLORFGBG` to a light background gets deeper shades.

What changed:

- **The state file moves to version 4 while it holds a pin.** sitboard 0.5.x and older refuse to start on it (exit code 1, saying it was written by a newer sitboard) and leave it unchanged. Once it holds no pin, the next save writes it as an older version again (3, 2 or 1, by what it holds), which 0.5.x opens; unpinning the last pin is such a save. To go back to 0.5.x with pins kept, move the file aside: it takes your seen marks, what Catch-up marked read, grouping settings and pins with it.
- The state file now also keeps the issues you pinned: for each, its forge, host, repository and number, when you pinned it and, once sitboard has learned from GitHub that it is closed, when it first learned it. A GitLab pin keeps no closed mark. `--state`, `--no-state` and the start lines now name pinned issues with what the state file keeps.
- From Claude Code transcripts and Codex rollouts, sitboard now also reads the session's own `gh issue` and `glab issue` commands for the issue they name. It keeps, in memory, only which tool it was, the repository (or, when the command named none, the folder it ran in), the issue's number and the time; never the command text.
- sitboard now also asks `git` about some of the folders a session's own issue commands ran in, when a command named no repository (for at most 32 further folders named only by issue commands), and, for the checkouts it asks about, reads each remote's fetch and push addresses and whether `gh` has a default repository set there (`remote.<name>.gh-resolved`, which `gh repo set-default` writes), to tell which repository such a command was about. These reads change nothing and are kept in memory.
- For GitHub, the issue lookups now also send the numbers of the issues you pinned in the repositories they already ask about, all of them, in the same lookups; there is no new call. Nothing about pins goes to GitLab.
- For GitLab, `glab` now also sends read-only lookups for the open issues of the GitLab projects of the projects on the board: their path, at most 8 to a call, in the same looks as GitHub's issue lookups and within their limit of 100 repositories a look. Each also asks for the address of the account glab is logged in with on that host (`currentUser`), which sitboard keeps in memory, per host name, to notice a change of account. After glab reports that GitLab rate limited a host, issue and merge request lookups to it wait for the time glab's message gives, at least a minute, or five minutes when sitboard cannot read a time from it. When an issue lookup finds that a host refused glab's token, that host is not asked about issues for five minutes, on any of its web ports, unless a login check made after the refusal passes before.
- The page now also gets, for the Issues panel, which cards are on each listed issue or looked at it (each card's id, and "on it" or "looked at"), how many listed issues have no agent seen (per project and in all), which issues you pinned, the pinned issues that are not among those listed, and whether the pins are kept only for this run. For a pinned GitHub issue outside the list it gets its number and link, "closed" once sitboard has learned it is, and, once GitHub has answered for it by number, what GitHub answered: title, milestone and its due date, labels, when it was last updated, and whether it is open or closed. For a pinned GitLab issue outside the list it gets its number and link. On either forge it also gets the cards whose open pull or merge request closes a pinned issue outside the list. A card also gets, for each listed issue its session looked at, its forge, host, repository, number and link, marked "looked at" (from Claude Code transcripts and Codex rollouts alike), not its title; an issue its own open pull or merge request closes is carried as "closes" instead. When an issue look finds a GitLab host's login gone, that host's issues leave the page.
- The page's API (`/api/v1`) is at contract version 24 (0.5.0: 20). It adds `POST /api/v1/issues/pin` with `{forge, host, repo, number, pinned}`, behind the same loopback, origin and token checks as the page's other actions, and these fields: in the snapshot, `kind` (`closes` or `looked`) on a card's issues, `issuesKey` and `issuesNoAgent` on projects and `noAgent` in the issues summary; in the answer of `GET /api/v1/issues`, `unsaved` and, per repository, `key` and `pinned` (the pinned issues outside the list), with `agents`, `pinned` and `state` on its issues. A page built for another version asks to be reloaded.
- tmux on Linux: when the pane's tmux server is shutting down (tmux 3.4, as on Ubuntu 24.04, says "server exited unexpectedly"), a jump now says the tmux session is gone, as for a server that has stopped, instead of "tmux did not answer".
- Website: in the two-column layout (windows 800 pixels wide or more), the headings of the "Three views" and "Nothing to set up" sections stay in view while their text scrolls, and README and the website spell out the name once: sitboard (situation board). The website's pictures show the Agent filter, the tags on issues and the pinned issues.

Limits:

- "Looked at" is read strictly: a link missed is better than an agent credited with an issue it never looked at. Plain `gh issue` and `glab issue` commands count; one in a more involved shell line (with variables, `cd`, `&&`, `||`, `env`, `sudo` and the like) may give none, and so may `glab issue … -R`. A command that names no repository is credited to the repository of the folder it ran in only when git tells that repository without doubt (a fork with its upstream stays unknown), as git last named it. `gh issue view 7 -R owner/name` with no host is read as github.com, and a `GH_REPO` or `GH_HOST` the session inherited is not seen.
- Coordinators: a session sitboard takes for a coordinator gives no "looked at"; its own open pull or merge requests still give "on it". So an issue only a coordinator looked at can say "no agent seen".
- "No agent seen", its counts on the tiles and the Agent filter are judged over the issues listed, up to 30 per repository; the issues behind "+N more" are not judged, and pinned issues outside the list are not counted.
- Pins: nothing is asked of GitLab for a pinned GitLab issue outside the listed 30, so its row shows no title and never shows it closed. Pinned issues outside the list do not show while a filter is on. A pin whose repository has left the board, or whose GitLab address has changed, is kept but not shown, and counts towards the 200, until that address is on the board again.
- GitLab issues: when glab switches to another account on the same host, sitboard notices it through a later issue lookup, not at once.
- A stopped sitboard: a sitboard that hangs without stopping keeps its connection open, so the page cannot tell it from one that is live.

## 0.5.0

Open GitHub issues per project, Codex sessions that ended before sitboard started in Catch-up, GitLab under a subfolder or on a port, and a "Caught up" that marks the list it was pressed on.

What is new:

- Issues. An Issues chip in the header adds up the open issues of the GitHub repositories of the projects on the board that GitHub has answered for, and shows that number when it is above zero. It opens a panel that lists the open issues of the projects you picked, read only, grouped by milestone (with a filter when there is more than one group, issues with no milestone being a group of their own): each issue's number, linked to GitHub, its title, labels and when it was last updated, up to 30 per repository and a link to the rest. Project tiles and rail rows show the open counts GitHub has given for a project's repositories (rail rows when above zero). GitHub only; `--no-github` turns it off.
- Catch-up now lists the finished turns and pull and merge requests of the Codex terminal sessions of the last 7 days that had ended before sitboard started, under the title Codex's session index holds for them (when it has one), as it does for Claude Code; they still get no card. When that start-up read is cut short (it has a time budget and leaves out a rollout larger than 512 MiB), the panel says items may be missing.
- GitLab under a subfolder of its host (such as `example.com/gitlab`) and GitLab hosts with a web port (such as `example.com:8443`) are supported; glab is asked about such a host by its name without the port (see Limits).
- The server keeps at most 32 of the page's event streams open at once; one more is refused (503) and that page tries again.
- `make audit` looks sitboard's Go and npm dependencies up in the vulnerability databases (govulncheck and `npm audit`). It needs the network, so it is not part of `make check`.
- README's generated sections (what it does, privacy, flags, requirements, what is not there yet) and the website's feature and privacy texts about the tool are built from one list of facts (`internal/facts/facts.yaml`), which `make check` checks against the code. The website's own wording, such as the home page's problem section and its cookie and analytics notice, is written by hand.

What changed:

- **After upgrading, the Catch-up items of the last 7 days are unread again** (a list holds up to 1000 of them). "Caught up" now marks read the items of the list the panel loaded, including those folded under "Show N more" in a project, and nothing else marks an item read: an item the list left out, one only another tab showed, or one sitboard first finds later, even if it happened earlier, stays unread until a list holds it and it is marked read, across restarts too while the state file can be saved. A list from before a restart, or one too old after newer lists, marks nothing, and neither does one that would keep more than 20,000 items marked read in the last 7 days; the panel says so. Opening the panel still marks nothing read.
- The state file no longer keeps a catch-up marker. It keeps when the newest list you marked read was made and, for each catch-up item marked read whose own time is in the last 7 days, a hash of the item's identity (not the identity itself) and that time; an older item is dropped on the next save. The first time 0.5.0 opens a state file of 0.4.0 or older, it drops that file's catch-up marker and the items it kept as unread, and saves the file at once; if that save fails, the run keeps what it marks read in memory only, says so when it starts and in the Catch-up panel, and the next start drops the marker again. `--no-state` keeps what Catch-up marked read in memory only, with the seen marks and groupings.
- **The state file moves to version 3 while it holds items marked read.** sitboard 0.4.0 and older refuse to start on it (exit code 1, saying it was written by a newer sitboard) and leave it unchanged. The first save after the last of those items is 7 days old writes it as an older version again. To go back to 0.4.0 sooner, move the file aside: it takes its seen marks and grouping settings with it.
- When it first sees a session in a running `claude` process, sitboard now keeps a fourth fact from the process's arguments: whether it was started with `-p` or `--print`, as a yes or no. A `claude -p` run started inside another session's agterm terminal no longer takes over that terminal: a run started with `-p` or `--print` (and an SDK run, once its transcript is read) gets no agterm terminal of its own. A headless run in a tmux pane can still offer the tmux jump when the pane passes sitboard's check.
- For the Issues panel, `gh` now also sends read-only lookups for the open issues of the GitHub repositories of the projects on the board: their owner and name, at most 20 to a call and 100 to a look. The first look runs once sitboard knows a repository to ask about, then about every ten minutes; a repository new to the board or the panel reading the list can start one sooner, never within a minute of the latest one's start nor while one is under way. Once GitHub's rate limit stops a look, issue lookups, and pull request and Leftovers lookups for the repositories that look asked about, wait five minutes; one that had already passed that check can still send its request.
- The page now also gets, for the Issues panel, the open issues of those repositories: for each repository its open count and up to 30 issues with their number, title, link, milestone and its due date, up to 5 labels and when each was last updated, plus each project's open count. A title, a milestone and a label hold whatever words they were given on GitHub; sitboard cleans them and shortens long ones before serving them. They are kept in memory only, never written anywhere. When an issue look finds the GitHub login gone, they leave the page.
- Of the Codex sessions that ended before sitboard started, the start-up read now keeps their model and effort, finished turns and pull and merge requests, besides their folder and token counts; the page gets the finished turns' times.
- The privacy statement now also says what 0.4.0 already did: files sitboard reads and writes go over the network when you keep them on a network folder (such as a `--state` file there), and that is what stays, with the board's own server on `127.0.0.1`, when `--no-github` and `--no-gitlab` together stop all traffic to GitHub and GitLab; sitboard never asks for a GitHub token, and keeps, logs and serves no GitHub or GitLab token; to find Codex's terminal clients it asks `ps` for the command lines of all your processes, looks only at those of `codex` itself and keeps from each a few facts about the process (its id, user and start time, what kind of Codex client it is, and a folder given with `--cd`); at start it creates an empty temporary file beside the state file and removes it, to check the folder can be written, and a lock file it can only read is left as it was; the page gets each card's id (the tool's name and the session's own id) and, with agterm, its terminal's agterm session id; and the page never gets the text of prompts and replies, the contents of files or whole tool results.
- The page now also gets, with the GitLab hosts it may link to, each host's web port, if its address has one, and the subfolder glab has for it (as in `example.com:8443/gitlab`).
- The header's Live chip is the same size as the other chips, and while connected it is green with a gently pulsing dot (still, with reduced motion).
- On a phone-width window the header's Spend chip no longer runs off the left edge: Codex's tokens move to a second line inside the chip, and the money total stays whole.
- Leftovers: when sitboard could not list every checkout of the repositories on the board (a repository git could not read, a session's folder git has not answered about yet, a check that ran out of time), the list says it may be incomplete, and a worktree with git-ignored files is held back instead of listed with a warning. Checkouts of GitLab and local-only repositories now hold back a GitHub worktree they sit in.
- A pull request address naming a repository "." or ".." is no longer read from a session's output.

Limits:

- Issues: GitHub only; GitLab projects show no issues. A repository lists up to 30 of its open issues, and the panel links to the rest on GitHub. Between looks (normally ten minutes apart) the list can be out of date; the panel says when it was read.
- GitLab: GitLab repositories are not in Leftovers. A host needs a dotted name and an HTTPS merge request address; glab is asked about a host by its name without the port: its login check and lookups go where glab's configuration for that name points, a port in a merge request address is used to check GitLab's answer, and two GitLab instances on different ports of one host cannot be told apart. A glab login stored under `host:port` is not used. glab's subfolder for a host may have up to 8 levels, and a project path with it up to 22. On GitLab Community Edition, which has no approval fields, no approval is shown.
- Catch-up: at most 20,000 items marked read from the last 7 days are kept; a "Caught up" that would pass that marks nothing.
- Codex: a session that waits for you to approve a command shows as blocked only with agterm. `codex exec` runs are not in Catch-up. A recently active session whose liveness sitboard cannot tell can still show, and count in Catch-up. When more Codex sessions are open than Codex terminals, which of them are live is a best guess, and when the terminals do not resolve to one agterm terminal, no jump is offered. Terminals are matched by folder: after sitboard restarts, a session resumed in a terminal in another folder can be missed. With one Codex session open and one Codex terminal in its folder, sitboard cannot tell that this terminal has the session open (say, while Codex's resume picker shows), and Jump may bring that terminal forward. Terminal sessions were checked with Codex 0.171 on macOS, and the token records with 0.166 to 0.171; `codex exec` was not checked again on 0.171. On Linux, terminal sessions, their lock (held by Codex's managed daemon) and `codex exec` were checked with Codex 0.172 (standalone install, arm64 container); `CODEX_HOME` elsewhere and an npm install were not run there.

## 0.4.0

Codex sessions on the board, GitLab merge requests, what each agent spends, a jump to tmux panes, a list of leftovers, and links in Lanes and Teams.

What is new:

- Codex sessions. Sessions of the Codex terminal client and of `codex exec` get cards next to Claude Code's: their model and effort, whether they are working, finished or blocked, the pull requests they created, the threads Codex started under them (as a count), and, for a terminal session, the agterm terminal to jump to. A Codex session's name is the title Codex recorded for it, if any (written by the model, or the one you gave it). An effort word that is not on sitboard's scale (a short lowercase word) is shown as written; "ultra" gets the same filled box as max. Threads of the Codex desktop app and of editor plugins are not shown. Catch-up lists the finished turns and pull requests of the Codex terminal sessions sitboard followed. sitboard reads Codex's session files and never changes anything in Codex's folder.
- Spend. Each agent's output tokens, when known, are on its card and in Teams, with a cost estimate at API list price for Claude Code sessions, from Claude Code's own price table (or the total Claude Code recorded when a session ended). A Spend button in the header gives today's figure and opens a Spend panel with each project's use per day for the last 7 days. Every amount is an estimate, marked "≈", never a bill. Use whose model has no price shows as "+ unpriced" beside the part that has one, or as tokens and "no price" when none has. Codex sessions show tokens only, since Codex keeps no price; the ones that ended before sitboard started, in the last 7 days, are counted too.
- A jump to tmux. A Claude Code card whose session runs in a tmux pane jumps to that pane when a tmux client is attached, with or without agterm; when that client runs inside agterm, sitboard tries to bring its agterm session to the front first.
- Leftovers. A quiet "N leftovers" link in the status bar lists merged work still on the machine that sitboard has evidence for: a worktree, branch or branch on GitHub whose pull request merged into the default branch, and idle sessions whose own pull requests all merged at least 24 hours ago. Each item links its merged pull request and says what sitboard checked, such as "merged · nothing uncommitted · not in use". Work that still holds something (commits after the merge, uncommitted files, a stash, a process in the folder) is only counted, except a worktree in use only by finished sessions that are themselves listed, shown as "in use by its session" (or "by a finished session"). sitboard removes nothing. It needs GitHub, so `--no-github` turns it off.
- In Lanes and Teams, the pull request and issue numbers a row shows are links to GitHub (to GitLab for a merge request and its issues), as on the Board; a click anywhere else on a row does what it did before (jump, or show the session's details to copy).
- GitLab merge requests. A merge request a Claude Code or Codex session created with `glab mr create`, or with `git push -o merge_request.create` (counted when GitLab's creation time falls within two minutes of that push), shows on its card and in Lanes and Teams the way a pull request does: `!12`, linked to GitLab, with its state, the issues it closes in its own project where GitLab gives them, and, for an open request, its draft flag, pipeline and approval ("approved" or "approval needed"). Catch-up lists it as opened and merged. One that glab reports as already existing is not the session's own. It works on gitlab.com and on self-hosted GitLab, on the hosts your own `glab` is logged in to (tested with glab 1.131.0). Once a merge request is on the board, the page says "pull or merge request" where it said "pull request". The status bar's GitLab line says whether glab answers and can name the host of a merge request glab is not logged in to ("not logged in to <host>"). `--no-gitlab` switches it off.

What changed:

- **No network traffic now needs both `--no-github` and `--no-gitlab`.** With `--no-github` alone, `glab` can still contact the GitLab hosts your sessions use; with `--no-gitlab` as well, there is no network traffic. With glab not installed, or with `--no-gitlab`, sitboard runs no `glab` at all.
- For GitLab, sitboard runs your own `glab` (found on your `PATH` or in the usual install folders), and asks GitLab only about a GitLab host that a session inside `--roots` points to: the host of a merge request it created or a push of its named, or of its folder's origin when that is not on github.com. `glab version` runs when sitboard starts (and each minute while it fails); while a session needs a host that is not github.com, `glab auth status` runs for it about once a minute until the check passes, then about every eight minutes. `glab auth status` is glab's own login check, and it contacts the host when glab has a login stored for it. Lookups go only to a host whose login check passed within the last ten minutes, gitlab.com included: they send the project's path or numeric id and the numbers of the merge requests a session created or a push of its named, and ask which issues such a merge request closes. No branch name goes to GitLab.
- glab runs in `/` with an environment sitboard builds, not your shell's: `PATH=/usr/bin:/bin`, `HOME`, `USER` and `LOGNAME` from the system's user list, the keyring's `DBUS_SESSION_BUS_ADDRESS` and `XDG_RUNTIME_DIR`, the proxy variables `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` (and their lowercase forms; `ALL_PROXY` is not passed), so a proxy you set sees which hosts glab talks to, and settings that turn off glab's telemetry, update checks, prompts, debug output and helper downloads. No token, host or config folder from your environment reaches glab. sitboard never reads glab's config file or a token itself, and glab's output is read for its answer and never logged.
- The page now also gets, for GitLab, the merge requests' numbers, titles, links, states, pipeline, approval and draft flag, the numbers and links of the issues they close, and project paths with their group. The GitLab hostnames of your projects' origins and of the merge requests, and the host named in the GitLab status line, appear on the page. A session's title can be its open merge request's title.
- A pull request that `gh pr create` reports as already existing is no longer shown as the session's own.
- When it first sees a session in a running `claude` process, sitboard now keeps a third fact from the process's environment: the tmux pane and its server's socket path, from `TMUX_PANE` and `TMUX`. For a session in tmux it asks `ps` for the terminal of the session's process and asks `tmux` once, on that pane's own socket and never starting a tmux server, whether the pane shows that terminal; only then does the card offer the tmux jump. When you jump, it asks `tmux` for that server's panes and clients and reads the arguments and environment of the tmux client it is about to move, keeping only its agterm session id. The pane, its terminal and the session process's id and start time stay in memory and never reach the page.
- sitboard now reads Codex's files when Codex's folder (`~/.codex`, or `$CODEX_HOME`) exists: the session files (rollouts) under its `sessions` folder (the first line of the recent ones and of those whose lock is held; the rollouts of running and recently active sessions; and, at start, those of the last 7 days, including ended sessions, for their folder and token counts), Codex's session index for each session's title, and the names of its lock files. It asks `lsof` (on Linux `/proc`) which process holds a session's lock file, without taking the lock. It finds the Codex terminal clients by their command line in `ps`, reads their environment, keeping only the agterm session id and whether `CODEX_HOME` is the folder it watches, and asks for their working folder when the command line does not give it; it drops what it read when it cannot confirm the process is still the same one. It never opens Codex's databases and writes nothing in Codex's folder. From a rollout the page gets only derived fields (model, effort, folder, pull requests, token counts); the only free text from Codex's files is a session's title.
- From `~/.claude.json` sitboard reads only Claude Code's price table (`additionalModelCostsCache`), at most once a minute; every other key in that file is read past and not kept. Token counts and estimated costs come from the transcripts it already read and from the cost line Claude Code writes when a session ends.
- For Leftovers, every 10 minutes (sooner when the board sees a merge or a listed session changes, at most once a minute) sitboard asks `git` about the worktrees, local and origin branches and stashes of the repositories on the board, and the local status of the worktrees that could be leftovers and of a main checkout where an idle session sits, read only: no fetch, no lock. It asks `lsof` (on Linux `/proc`) for each of your processes' parent and working folder, kept for that look only. Its GitHub lookup now includes up to 100 branch names from each clone on the board: local branches (never-pushed ones included) first, then origin branches. Stash messages, file names from `git status`, which process works where and commit ids stay in memory: they are not served, written to disk or logged.
- The page now also gets token counts and estimated costs, a Codex session's title, and, for Leftovers, the home-relative worktree and clone paths and branch names of merged work still on the machine, the merged pull requests, counts of held-back items by reason, and when that list was made. The state file's format is unchanged; its seen marks now include Codex sessions' ids.

Limits:

- Codex: a session that waits for you to approve a command shows as blocked only with agterm. Codex sessions known only from the start-up read for Spend get no card and are not in Catch-up; nor are `codex exec` runs. A recently active session whose liveness sitboard cannot tell can still show, and count in Catch-up. When more Codex sessions are open than Codex terminals, which of them are live is a best guess, and when the terminals do not resolve to one agterm terminal, no jump is offered. Terminals are matched by folder: after sitboard restarts, a session resumed in a terminal in another folder can be missed. With one Codex session open and one Codex terminal in its folder, sitboard cannot tell that this terminal has the session open (say, while Codex's resume picker shows), and Jump may bring that terminal forward. Terminal sessions were checked with Codex 0.171 on macOS, and the token records with 0.166 to 0.171; `codex exec` was not checked again on 0.171, and on Linux the Codex part is built from the documented layout and not yet tried.
- Spend: Codex shows no amounts, only tokens. Compressed (`.zst`) Codex rollouts are not read, and of the ones that ended before sitboard started it reads at most 4000 files of up to 512 MiB each. A thread spawned under a Codex desktop-app thread counts nowhere. A few Claude Code cases can leave a card's figure a little off until sitboard restarts (for example a session that goes back to a folder it ran in before). With `--roots`, Spend counts only the sessions under those folders.
- tmux: a socket directly in a shared folder such as `/tmp` gets no tmux jump (tmux's default folder is fine). The tmux jump is tested against tmux on Linux; on macOS it has not been tried with a real tmux yet.
- Leftovers: the list says when it was made; between looks (normally 10 minutes apart) it can be out of date. It sees only your own processes, so another user working in a worktree is not seen. Git-ignored files or folders (an `.env`, a local database) do not hold a worktree back; their count is shown, a wholly ignored folder counting once. In a fork, a pull request into the upstream repository gives no evidence for its branch or worktree. GitHub only.
- GitLab: GitLab repositories are not in Leftovers. A host needs a dotted name and an HTTPS merge request address without a port; GitLab under a subfolder of its host (such as `example.com/gitlab`) is not supported. A merge request created by a push counts only when that push is the only one in its command; Codex records only when a command finished, so a Codex push that ran longer than two minutes can be missed. A merge request recorded only in an older transcript of a session resumed in another folder is not shown, as for pull requests. On GitLab Community Edition, which has no approval fields, no approval is shown. After `glab auth logout`, a host's merge requests leave the cards and Catch-up, usually within about ten minutes, and come back after a new login. A session whose origin is on another forge that is not GitHub (Bitbucket, say) still costs a `glab auth status` for that host about once a minute. Until a merge request is on the board, the page says "pull request".

## 0.3.0

Catch-up, a critter for every agent, effort levels, links on cards, a tap on the shoulder when an agent needs you, and grouping you can set.

What is new:

- Catch-up. The Catch-up button in the header says how many items are new and opens a panel over the current view: what happened since you last pressed "Caught up", up to 7 days back, grouped by project. It lists finished turns, pull requests opened and merged, and artifacts published. Opening it marks nothing read; "Caught up" does. It covers the Claude Code sessions that ran in the last 7 days, including those that had already ended before sitboard started, which it finds by their transcripts; while it is still reading those, the panel says so.
- Every agent has a critter: a small creature drawn from its session, the same in every view and after a restart. Its eyes, its outline and the line under its feet show the agent's state. It takes the place of the state dot on cards, in the needs-you queue, in Teams rows and in Lanes; the columns and words still say the state. Critters move only while you can see them, and with reduced motion they stay still.
- Cards show the session's effort level (low, medium, high, xhigh or max) next to its model, on the Board, in Lanes and in Teams: the level the session's latest reply ran at or, before its first reply, the level it was started with, marked "at launch". From high up the level's box is filled, deeper at each step, so high, xhigh and max stand out; a level set at launch is not filled, and on the Board its box is dashed.
- A tap on the shoulder. The tab's title ("(3) sitboard") and its icon show how many agents need you, and the icon shows a "?" when the board is not live. Turn on Notify in the header for a desktop notification when an agent starts needing you: for one agent it says why, for several how many, and it never names an agent, a project or a task. It stays quiet while the board is in front of you. The switch is off until you turn it on, and the choice holds for every tab of that board's address in that browser.
- Pull requests on a card, and the issues they close, are links to GitHub, opened in a new tab without a referrer. Their numbers are underlined and carry a small ↗, as do the pull request links in Catch-up, so a link is visible without hovering.
- Grouping settings. A project with parts can be set to "Always group", so its folder keeps grouping, and the "Forget grouping" confirm now offers "Forget once" or "Never group". The status bar says when folders have a setting and opens their list, where each can be set back to auto.
- `--state <file>` gives a board its own state file, and `--no-state` keeps seen marks, the catch-up marker and groupings in memory only, for a run that saves nothing.

What changed:

- One state file, one board. A second sitboard on the same state file now refuses to start (exit code 1). Until now it started a second board, and the two silently overwrote each other's seen marks and groupings. Give the second one its own file with `--state <file>`, or run it with `--no-state`. A lock file, `state.json.lock`, now sits beside the state file: a running sitboard writes its process number and machine name there, and a clean stop empties it. On a folder that does not support locks, sitboard warns and runs without the lock. sitboard 0.2.0 and older take no lock, so they are not stopped; when another program, such as an older sitboard, has changed the state file, the board warns once before its next write replaces those changes.
- sitboard refuses to start when the state file cannot be used (a folder it cannot write to, or a file that is not a sitboard state file), instead of failing at the first save or replacing another program's file.
- A card's pull request lines are no longer part of its jump button: a click on a pull request opens it.
- Haiku's model colour is a brighter lime.
- sitboard now reads the transcripts of the Claude Code sessions that ran in the last 7 days, not only of running ones, to find the sessions that had ended before it started. It keeps only the facts it derives from them, in memory.
- When it first sees a session in a running `claude` process, sitboard reads the process's arguments and environment, as before for the agterm session id. It now keeps a second fact from them: the effort level the session was started with (the `--effort` flag or `CLAUDE_CODE_EFFORT_LEVEL`), as one of the five level words. On Linux it now also reads `/proc/<pid>/cmdline` for this. Every other argument and variable is read past and not kept, logged or served.
- The page now gets a second piece of free text from a transcript: when the session's own record has no name (as for a session that has ended), the name Claude Code recorded for it in the transcript (yours, or one it made itself, for example from a plan), cleaned and shortened. When the record has the name, the page got it from there already. The page also gets the effort levels, and the home-relative paths of the folders you set to always or never group (up to 200), whether or not an agent works in them.
- The state file also keeps the folders you set to always or never group, and, for catch-up items that are still unread although they happened before the moment you marked, a hash of each item's identity (not the identity itself) and its time, at most 1000. A state file that holds a grouping setting is written as version 2; one without stays version 1. Upgrading needs nothing: 0.3.0 reads the files of 0.2.0 and 0.1.0 as they are.

Limits:

- Links on cards are on the Board only, not yet in Lanes or Teams.
- Catch-up does not cover: sessions that ran more than 7 days ago; sessions whose transcript Claude Code has already removed; `claude -p`, SDK and MCP-server runs; and, after a restart, something that happened before the moment you marked but that sitboard learned only after the restart (say, a merge GitHub reported late). What it had learned before stopping stays unread, up to 1000 items; after a crash, what arrived in its last 10 seconds may not. Of the repositories known only from sessions that had already ended, GitHub is asked about the 20 newest; pull requests in the others are not listed. With `--no-state`, Catch-up lists the last 7 days again after every start.
- The effort level "at launch" can differ from the one the first reply runs at: when `CLAUDE_CODE_EFFORT_LEVEL` is set in a Claude Code settings file, or when the model cannot run that level.
- Desktop notifications need your browser's permission; sitboard on another port asks again.
- If you go back to 0.2.0 or 0.1.0 after setting a folder to always or never group, it refuses to start: it says the state file "was written by a newer sitboard (file version 2, this build reads up to 1)" and leaves the file as it is. Before going back, set every folder back to auto (the file is then version 1 again), or move the state file aside. A version 1 file opens in them as before; on their next write they drop the catch-up items still unread behind the marker, which then count as read.

## 0.2.0

Model names in colour, links to the artifacts a session published, and a way to undo a project grouping.

What is new:

- Cards on the Board link the artifacts their session, or one of its in-process subagents, published on claude.ai, newest first, under its pull requests. A click opens the artifact in your browser. When there are more than three, the card shows the two newest and "+N more".
- Forget a project grouping. Select a project with parts and press "Forget grouping" (in the tiles, at the end of its parts row; in the rail, under its parts), then confirm. Its parts are no longer grouped under it, at once, and the folder does not group again until no agent has sat in it for two minutes. A grouping that forms after that is new, for example when two sessions are opened in that folder again, and can be forgotten again.

What changed:

- Claude model names show in their family's colour (Fable, Opus, Sonnet, Haiku) on Board cards, in Teams and in Lanes. In Lanes, a line that needs you or has failing checks keeps that line's colour instead. A model from another maker, or a Claude family sitboard does not know, gets no family colour; a card with no model says "model unknown" in a dashed, muted chip.
- The page now gets one piece of free text from a session's transcript: the title of each artifact the session published, as its own publish reported it, cleaned and shortened. Until now only identifiers, session names and times were taken from a transcript: the model id, the working folder, the pull requests the session opened, the names and terminal ids of the sessions it started, and the names of the sessions it heard from. Prompt text, code and tool output are still never shown and never served.
- sitboard's state file (`~/Library/Application Support/sitboard/state.json` on macOS; on Linux `$XDG_STATE_HOME/sitboard/state.json`, by default `~/.local/state/sitboard/state.json`) kept which cards you marked seen and which folders group projects. It now also keeps the folders whose grouping you forgot, so a restart does not group them again.

Limits:

- Artifacts: only the ones a session, or one of its in-process subagents, published itself (an update of another session's artifact counts as a publish). A rename made later elsewhere is not seen: the card shows the title from the session's latest publish. A deleted artifact stays listed. Claude Code sessions only, and on Board cards only, not in Lanes or Teams.
- If you go back to 0.1.0, it drops the forgotten groupings from its file on its next write, and those folders may group again.

## 0.1.0

The first release: a live board of the Claude Code sessions running on your machine.

Run `sitboard` and it opens the board in your browser. It finds the sessions by itself; nobody creates tasks, and the agents need no setup.

What it shows:

- A card per live session, with its name or title, its project, its status (working, blocked on a question or a permission, finished), the model, and how long it has been in that state.
- The columns, in board order: Needs you, Working, With coordinator, In review, Done · 24h and Idle. Working that has gone quiet for too long is flagged as stale (`--stale-after`, 20 minutes by default).
- Who spawned whom: a coordinator's workers sit under it, worked out from the sessions' own records.
- The pull requests a session opened, with their state, checks, review decision and the issues they close, read through your own `gh`, read-only.
- Three views: Board (one column per state), Lanes (one row per project, with a "Needs you" strip on top) and Teams (your queue beside one panel per coordinator with its workers).
- Project tiles or a side rail (switchable) choose which projects every view shows; a project that spans several repositories shows as one entry with its parts.
- Mark a finished card as seen. With the agterm terminal, jump to a session's terminal in one click, get better card titles, and mark a session seen by selecting it in agterm. Without agterm, clicking a card shows the session's folder and name to copy.
- The page gets names, titles, folder paths, states and pull request links, never session text.
- `sitboard --licenses` prints sitboard's licence and the third-party notices; the page links to them.

Not in this release yet:

- Codex sessions: only Claude Code sessions are shown.
- Catch-up: what happened since you last looked.
- Leftovers: merged work whose worktree, branch or session still exists.

Tested on macOS. The Linux builds are made and checked, but not tested by us on a Linux desktop.
